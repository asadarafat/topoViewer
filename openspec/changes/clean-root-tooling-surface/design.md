## Overview

This change separates two concerns that currently blend together:

1. root directory cleanliness;
2. npm script discoverability.

The root does not need to be empty. It needs to be intentional. A public
repository should show standard project metadata, source roots, docs, labs, and
automation clearly. Local caches, generated review artifacts, and private agent
state should not be part of the perceived project shape.

The root `package.json` has the same issue. It should expose the commands a
new user, CI workflow, release maintainer, or lab operator needs. It should not
expose every internal helper as a first-class command.

## Feasibility Iteration

Implementation feasibility after checking the current repo:

- **Low risk:** documenting root classification, documenting local cleanup
  targets, auditing ignore sources, and adding maintainer command taxonomy.
- **Medium risk:** adding docs/Grafana/check dispatchers while retaining
  compatibility aliases, because many docs and lab files reference current
  command names.
- **High risk:** removing `ci:*`, `dependency:advisories`, or
  `security:health-report`, because GitHub workflows and
  `scripts/check-public-readiness.mjs` currently depend on exact names.

Therefore the first implementation should keep public/docs/CI/lab aliases and
reduce only internal aliases after reference migration proves they are unused.

## Script Taxonomy

Root scripts should be classified before deletion:

- **Public common commands**: expected in README and day-to-day use.
- **CI commands**: stable commands used by GitHub Actions.
- **Maintainer commands**: release, artifact, API, docs sync, security, and
  generated-output checks.
- **Lab commands**: Grafana and Containerlab workflows.
- **Internal helpers**: implementation details that can move behind a
  dispatcher or direct `node scripts/...` invocation.

The long-term target root command surface should be roughly 20-30 scripts. The
first implementation pass does not need to reach that number. It must reduce
obvious internal aliases without breaking public docs, CI, release, security,
or lab workflows.

The stable command contract starts with:

```text
dev
build
test
lint
quality
ci
docs:preview
docs:build
grafana:lab:up
grafana:lab:down
grafana:clab:bundle
pack:check
```

Additional stable aliases may remain when they are documented public or CI
entrypoints. Everything else should either be:

- moved behind `npm run ci -- --lane <lane>`;
- moved behind a domain dispatcher such as `npm run docs -- <command>` or
  `npm run grafana -- <command>`;
- invoked directly by a script or workspace command where it is truly internal;
- retained temporarily with an explicit deprecation/migration note.

## Protected First-Pass Aliases

Some aliases are too widely referenced or explicitly checked to remove in the
first cleanup pass. They must remain unless every live reference, workflow, and
readiness assertion is migrated in the same patch.

Protected first-pass aliases:

- all scripts invoked directly by `.github/workflows/**`, including publish and
  security workflows;
- all `ci:*` aliases, especially `ci:docs` and `ci:public-readiness`;
- all scripts asserted by `scripts/check-public-readiness.mjs`, including
  `dependency:advisories`, `go:vulncheck`, `security:health-report`,
  `install:check`, `install:check:mkdocs`, `artifact:check`,
  `artifact:check:docs`, `artifact:check:package`,
  `check:object-reference`, `examples:audit`, `check:public-readiness`, and
  `test:hostile-content`;
- `dist:mkdocs`;
- `wheel:mkdocs`;
- `inspect:mkdocs`;
- `docs:preview`;
- commands advertised in the root README, package READMEs, published docs, lab
  docs, and maintainer docs, including `validate:schemas`,
  `validate:semantics`, `lint`, `build`, `pack:check`, `grafana:lab:up`, and
  `grafana:clab:bundle`;
- `vscode:harness`;
- `grafana:lab:*`;
- documented `grafana:clab:*` commands, including `up`, `down`, `smoke`,
  `bundle`, `rules`, and `traffic:*`.

Known coupling:

- `scripts/check-public-readiness.mjs` currently asserts exact script names
  including `ci:public-readiness`, `dependency:advisories`, and
  `security:health-report`, plus multiple install, artifact, docs, API,
  security, and public-readiness commands;
- GitHub workflows currently invoke multiple `ci:*`, npm publish, PyPI publish,
  docs, package, and security commands directly;
- public and maintainer docs currently reference `docs:preview`,
  `vscode:harness`, and several `grafana:clab:*` commands.

If implementation chooses to migrate any protected alias, it must update the
readiness checker, GitHub workflows, docs, helper messages, and generated
content in the same change.

## Implementation Sequence

The safe order is:

1. record baseline root and script inventories;
2. document root cleanup policy without changing tracked behavior;
3. add any dispatcher commands while keeping all existing aliases;
4. validate that existing public, CI, docs, publish, security, harness, and lab
   surfaces still work;
5. migrate references to preferred dispatcher forms only where that improves
   clarity;
6. remove only internal aliases with no live references and no readiness
   assertions;
7. run final surface validation and full CI.

Do not combine "add dispatcher" and "delete many aliases" in one unvalidated
step. A dispatcher is first a compatibility layer; script removal is a later
reference-proven cleanup.

The implementation checklist must follow this order. A later step may prepare
notes for an earlier decision, but it must not delete aliases before the
baseline, protected-alias matrix, dispatcher compatibility checkpoint, and live
reference migration are complete.

## Surface Preservation Matrix

Every implementation patch must preserve or atomically migrate these surfaces:

| Surface | Commands or checks that must still work |
|---|---|
| React/TypeScript package | `npm run build`, `npm test`, `npm run pack:check` |
| MkDocs/Zensical/docs | `npm run docs:build`, `npm run docs:smoke`, `npm run ci:docs` |
| Browser harness | `npm run vscode:harness` for local preview and `npm run ci:test:harness` for validation |
| CI lanes | all current `ci:*` aliases unless workflows and readiness checks are migrated |
| npm publish preflight | `npm run ci`, `npm run install:check`, `npm run artifact:check:package`, `npm run dependency:advisories` |
| PyPI publish preflight | `npm run ci:build`, `npm run dist:mkdocs`, `npm run inspect:mkdocs` |
| Security workflow | `npm run ci:public-readiness`, `npm run dependency:advisories`, `npm run go:vulncheck`, `npm run security:health-report` |
| Grafana Docker Compose demo | `npm run grafana:lab:up`, matching smoke commands, and `npm run grafana:lab:down` |
| Grafana Containerlab demo | documented `grafana:clab:*` commands and no leftover containers after validation |

If a command is replaced by a dispatcher form, the replacement must be reflected
in the surface's docs/workflow/readiness checks in the same patch.

## Long-Running Command Validation

Some commands are services, not finite checks. Validation must not blindly run
them as ordinary blocking commands.

Commands requiring controlled start/probe/stop validation:

- `npm run docs:preview`;
- `npm run vscode:harness`;
- `npm run grafana:lab:up`;
- `npm run grafana:clab:up`.

For these commands, validation must:

1. start the service in a controlled background process or use the existing
   smoke script;
2. probe the expected URL, port, or health endpoint;
3. stop the process or lab;
4. fail if cleanup leaves containers or servers running.

For docs validation, prefer `npm run docs:build`, `npm run docs:smoke`, and a
controlled `docs:preview` probe only when preview behavior changes.

## Dispatcher Direction

The existing `scripts/ci.mjs` already proves the lane-dispatcher model works.
This change should extend that pattern conservatively.

Recommended dispatchers:

- `scripts/ci.mjs`: keep as the CI lane owner.
- `scripts/docs.mjs`: docs preview/build/lint/smoke/sync commands.
- `scripts/grafana.mjs`: synthetic lab, Containerlab lab, bundle, smoke, and
  traffic commands.
- `scripts/sync.mjs`: content/docs/examples/generated projections.
- `scripts/check.mjs`: artifact/install/API/public-readiness checks.

Each dispatcher must:

- support `--help` or invalid-command output;
- fail fast with a clear message;
- preserve current environment-variable behavior;
- call existing scripts rather than reimplementing business logic.

## Compatibility Strategy

Script removal must be reference-driven:

1. inventory all script references in GitHub Actions, README, docs, package
   READMEs, labs, scripts, and OpenSpec active changes;
2. migrate references to the new stable command or dispatcher form;
3. keep compatibility aliases for one change if removing them would create
   avoidable churn;
4. remove aliases only after `rg` proves no live reference remains outside
   archived OpenSpec history;
5. run full CI before archiving.

Archived OpenSpec files do not need to be rewritten for historical command
names.

Live-reference searches must distinguish:

- live source, docs, package READMEs, workflows, scripts, and active OpenSpec;
- generated projections that must be updated from canonical content;
- archived OpenSpec history, which remains historical and does not block
  migration.

## Documentation Contract

README should show only the normal user/developer commands:

- `npm ci`;
- `npm run ci`;
- focused checks such as `npm run lint`, `npm run build`, `npm test`,
  `npm run pack:check`;
- `npm run docs:preview`;
- `npm run grafana:lab:up`;
- `npm run grafana:clab:bundle`.

Maintainer docs should carry the full command taxonomy and advanced dispatcher
usage.

Root cleanup guidance should explain which local entries are already ignored and
which unignored generated/local entries were added to repo `.gitignore`.
Already ignored entries should not become the main implementation workload.

When classifying local-only files, the implementation must record whether each
entry is ignored by repository `.gitignore`, `.git/info/exclude`, global Git
ignore, or not ignored. Only repository `.gitignore` should be changed by this
project unless there is a repo-wide reason.
