## Why

TopoViewer is now much more capable than its documentation suggests. The docs
show features, but they do not yet make the product feel complete, trustworthy,
or easy to adopt.

The current documentation has strong raw material:

- canonical content under `packages/topoviewer/content/**`;
- live examples with topology and stylesheet YAML;
- MkDocs and Zensical builds;
- a React package;
- a browser harness and experimental VS Code package;
- schema validation, semantic linting, style defaults, CLOS layout, attention,
  regions, paths, callouts, and production hardening.

The problem is completeness and packaging. Users still have to infer too much:

- where to start;
- which page answers which question;
- what every YAML field accepts;
- what every style key does;
- what a live example is supposed to demonstrate;
- how to debug common failures;
- how to embed and ship TopoViewer in a real environment.

This change makes documentation a product surface, not a generated byproduct.

## What Changes

### 1. Define a production-grade docs contract

Add a durable docs standard that every public capability must satisfy:

- concept coverage;
- task-oriented guide when the capability is used by authors;
- reference coverage for YAML fields, style keys, or TypeScript APIs;
- live example with expected behavior;
- validation and troubleshooting guidance where relevant;
- MkDocs and Zensical parity.

### 2. Restructure documentation around user journeys

Rework the public docs information architecture into clearer sections:

- Overview;
- Get Started;
- Concepts;
- Authoring Guides;
- Reference;
- Examples;
- Integrations;
- Production;
- Contributing/Documentation Standards.

Keep the canonical source in `packages/topoviewer/content/**`.

### 3. Add missing authoring and integration guides

Add task guides for the workflows users actually need:

- first topology;
- style a topology;
- add labels and data;
- add layers;
- add regions;
- add paths;
- use attention;
- choose a layout mode;
- validate YAML;
- debug a blank or wrong diagram;
- embed in MkDocs;
- embed in React;
- preview through the browser harness;
- understand Zensical output.

### 4. Turn reference pages into complete references

The reference model must become a real field reference, not only a conceptual
overview.

Add or generate complete reference coverage for:

- topology document fields;
- graph object fields;
- diagram primitive fields;
- layout fields;
- attention fields;
- renderer limits;
- stylesheet selectors and style keys;
- MkDocs fenced block options;
- TypeScript exports and stability.

### 5. Make examples teach, not only render

Every public example page must explain:

- what the example demonstrates;
- what the user should expect in the live viewport;
- which YAML block matters;
- when to use the feature;
- common mistakes when relevant.

The generated live viewport / topology YAML / stylesheet YAML structure remains
the default public example format.

### 6. Harden docs quality gates

Add checks so future docs cannot quietly regress:

- no undocumented public style keys;
- no undocumented exported public APIs unless explicitly marked internal;
- no example without required explanatory sections;
- no broken local links or anchors;
- no unexpected MkDocs nav/orphan warnings;
- no generated content drift;
- MkDocs and Zensical output both include the same critical pages and live
  viewport assets.

## Capabilities

### New Capabilities

- `production-grade-docs`: a documentation contract, structure, and validation
  strategy for the public TopoViewer docs.

### Modified Capabilities

- `topoviewer-documentation`: gains task guides, complete references, stricter
  IA, and docs-quality checks.
- `topoviewer-examples`: gains explanatory acceptance criteria for public
  examples.
- `topoviewer-reference`: gains complete YAML, style, integration, and API
  coverage.
- `topoviewer-docs-build`: fails on documentation drift that would hide missing
  or incomplete public content.

## Impact

- `packages/topoviewer/content/pages/**` - source-of-truth docs content.
- `packages/topoviewer/content/examples/**/README.md` - richer example
  explanations.
- `packages/topoviewer/content/examples/catalog.yaml` - optional metadata for
  use cases, expected behavior, and docs grouping.
- `scripts/sync-docs-site.mjs`, `scripts/sync-examples.mjs`,
  `scripts/sync-zensical-docs.mjs` - possible generation updates for new IA and
  example page structure.
- `mkdocs.yml` and `zensical.toml` - nav updates.
- docs validation scripts - new checks for links, API/reference coverage,
  example section coverage, and nav warning allowlists.
- `README.md` and `docs/index.md` - clearer boundary and less duplicate pitch.

## Non-Goals

- Do not change renderer behavior.
- Do not redesign the website visual theme in this change.
- Do not remove MkDocs or Zensical.
- Do not make Zensical the canonical source; it remains generated from shared
  docs content.
- Do not document private or customer-specific topology material.
- Do not add network-vendor-specific assumptions to the generic TopoViewer
  model.
